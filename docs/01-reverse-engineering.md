# 逆向分析与证据记录

## 1. 结论

两份 PDF 不是孤立的文档模板，而是飞书 Base `申汰PCO管理系统` 的排版打印结果。现有 Base 已经覆盖客户、方案、工程师、服务单、封堵和收支对账，但数据模型存在明显的“选项膨胀”和关联缺失。

系统设计的重点应放在：

1. 把隐患点变成一等对象。
2. 把长文本选项拆成主数据、模板和自由文本。
3. 把报告变成结构化数据的版本化快照。
4. 把高风险、逾期复检、证据缺失变成可执行的运营队列。

## 2. 方法

### 2.1 PDF 结构解析

- 使用 Poppler `pdfinfo` 读取页数、页面尺寸、元数据。
- 使用 `pdfplumber` 提取文本、表格和页面布局。
- 使用 `pypdf` 统计字体、XObject、图片数量。
- 使用 `pdftoppm` 渲染页面，用于版式核对。

### 2.2 REA

- 对 PDF 调用 `open_binary`，返回 `target_unavailable / unsupported_target`，说明 REA 当前不支持把 PDF 作为二进制分析目标。
- 对飞书 Base 使用 `capture_browser_scenario`，证明该 Base 在没有登录凭据的隔离浏览器中可只读打开，并跳转到 `tblUjERiARgOMvmR` 视图。
- REA 证据 ID：`ev_cdaf6d72427474475f884d9cfe1823dadce674535879237fdf783e2b2e712fbc`。
- 该证据的 `completeness.status` 为 `incomplete`，网络事件达到采集预算；因此浏览器场景只用于证明可达性与页面标题，不作为完整数据清单。

### 2.3 飞书 Base 只读盘点

- 使用隔离 Chromium 打开 Base，读取导航与可访问性树。
- 飞书表格内容渲染在 canvas 中，DOM/可访问性树不暴露单元格。
- 通过同一浏览器会话读取 `clientvars` 响应，解码其中的 gzip/base64 JSON，获得表结构、字段、视图和记录聚合。
- 未调用任何写接口，未修改 Base。

## 4. 关键发现

### 4.1 多选字段膨胀

| 字段 | 选项数 |
| --- | ---: |
| 服务内容与简介 | 208 |
| 建议解决方案 | 130 |
| 风险点描述 | 111 |
| 处理方法 | 66 |

这些字段本质上是长文本，被做成了多选选项。结果是：

- 选项无法复用和治理。
- 报告内容不可结构化查询。
- 同一含义出现多种写法。
- 新增业务只能继续加选项。

### 4.2 关联覆盖不足

- 186 个客户中，54 个关联服务单，56 个关联封堵报告。
- 0 个客户有合同附件。
- 这意味着“客户 → 服务 → 封堵 → 复检”的链路在数据层并不完整。

### 4.3 风险与证据

- 服务单风险：高风险 88、中风险 54、潜在风险 50、极高风险 1、未填写 2。
- 风险图片：189/195 有附件。
- 完工照片：193/195 有附件。
- 服务人员签字：187/195。
- 现场负责人签字：186/195。
- 物料使用：193/195。
- 处理方法：172/195。

高风险单据占比高，但现有 Base 没有独立的复检闭环表，系统应把“高风险”直接转成任务和提醒。

### 4.4 月度视图

服务单存在 `3月份报告` 到 `8月份报告` 等视图，说明当前按月出报告。系统应保留按月筛选和导出，但不把“月份”做成物理表。

### 4.5 封堵表的可见性

`tblT6csxWufRBW2e` 是客户表关联的封堵报告表，但 guest 会话读取其 schema 时没有返回字段。因此：

- 封堵表结构以 PDF `STFD-2026-116` 为准进行推断。
- 正式迁移前，需要在登录状态导出该表字段和样例记录。

## 7. 对设计的直接影响

1. 不做“飞书表格克隆”，做领域模型。
2. 以 `Finding` 串联勘测、封堵、复检和报告。
3. 用模板 + 主数据替代 208/130/111 个选项。
4. 把报告编号、版本、签名、照片哈希纳入数据模型。
5. 工作台以风险队列和逾期复检为第一屏，而不是以列表为第一屏。
